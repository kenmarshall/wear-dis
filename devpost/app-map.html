App Map

Wear Dis

Describe an event (or tap a category), answer a few tailored questions, and get five complete outfits, ranked best first. Each one explains why it suits the occasion and why the colors work, and links every piece to Amazon search results.

The main pieces

  • One page, several steps: app/page.tsx is the flow controller. It holds all session state and shows one step component at a time.
  • Step components in components/: EventInput, FollowUpQuestions, LoadingState, OutfitList/OutfitCard, ErrorMessage.
  • Two server routes, app/api/questions and app/api/outfits, keep the API key on the server and call Claude through lib/claude.ts.
  • Shared rules in lib/: zod schemas and cleanup (schemas.ts), the stylist prompts (prompts.ts), Amazon link building (amazon.ts), and all on-screen text (strings.ts).
  • Nothing is stored. Refresh the page and it starts over.

One action, end to end: “Find my outfits”

Reference route: three stops

A reference route through the current code. It wasn't toured interactively; follow it any time to see how the same action is built.

  1. app/page.tsx → handleAnswers, runGuarded Once you've answered the questions, handleAnswers saves your Men's/Women's choice, switches to the loading step, and calls fetchOutfits. runGuarded is the double-tap guard. If anything throws, it remembers a retry closure (retryLast), so Try again resends exactly the same answers.
  2. app/api/outfits/route.ts → POST · lib/claude.ts → getOutfits, askForJson The route validates the request body with OutfitsRequestSchema, so the gender and answers are required. Then getOutfits sends OUTFITS_SYSTEM_PROMPT plus buildOutfitsUserMessage to Claude, with a zod output format, so the reply arrives already parsed into the Outfit shape. Refusals and empty output become an AdvisorError, and the route turns that into a 500 that shows the friendly error screen.
    Why there's also code-side cleanup

    The schema avoids length and regex limits so it works with structured outputs. finalizeOutfits in lib/schemas.ts enforces the rest: it drops empty outfits, requires at least five, sorts by rank, and renumbers 1–5. The tests in tests/schemas.test.ts cover it.

  3. components/OutfitCard.tsx · lib/amazon.ts → buildAmazonSearchUrl Each card draws every piece with PieceIllustration (an SVG tinted with colorHex). When expanded, it adds the two “why” sections and one link per piece. The link is a search URL built from color + search terms + men's/women's, e.g. 
    https://www.amazon.com/s?k=Navy+unstructured+blazer+men%27s
    It's a search, not a product lookup, which is why results are approximate.

A practice to reuse

Decide the boundary before you build, so late feedback is cheap to judge.

In final review, the Amazon results often didn't match the piece description. It wasn't a surprise and it didn't cause rework: scope.md > Explicitly Cut had already recorded that exact matches would need Amazon's product API (an approved affiliate account), and that search links were the deliberate stand-in. Likewise, the idea of showing all card details up front was weighed against a named cost (the results page roughly doubling in length) and declined, leaving prd.md > Ranked Outfit Results unchanged.

On your next project, write down each cut with its reason during scoping. When testing turns up something that “feels off”, check it against that list first. If it's an already-accepted tradeoff, it becomes a roadmap item, not a bug.
